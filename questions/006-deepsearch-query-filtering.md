## 1. 为什么需要 Query 筛选和难题构造？

### 一句话回答

DeepSearch 系统（如 Perplexity、OpenAI Deep Research、Grok DeepSearch）的核心能力是**多步推理 + 检索增强**。要训练和评估这种能力，需要"简单问题回答不了、必须深度搜索才能解决"的 query——这就是 query 筛选和难题构造的意义。

### 更完整的动机

| 动机 | 解释 |
|------|------|
| **训练信号** | 如果问题太简单（一步检索就能答），模型学不到"何时该继续搜"的策略 |
| **评估区分度** | 简单题所有模型都能答对，无法区分系统优劣 |
| **数据效率** | 标注成本高，应把预算花在最有价值的样本上 |
| **安全对齐** | 难题更容易暴露模型的幻觉和推理错误 |

## 2. 核心概念速览

```
┌─────────────────────────────────────────────┐
│              Query 质量空间                    │
│                                             │
│   ┌───────┐    ┌───────┐    ┌───────┐      │
│   │ 难度  │    │ 多样性 │    │ 可验证│      │
│   │Difficulty│  │Diversity│  │Verifiability│ │
│   └───┬───┘    └───┬───┘    └───┬───┘      │
│       │            │            │           │
│       └────────────┼────────────┘           │
│                    ▼                        │
│            ┌──────────────┐                 │
│            │ 最终入选 Query │                │
│            └──────────────┘                 │
└─────────────────────────────────────────────┘
```

**三大黄金指标：**
- **难度（Difficulty）**：模型/人类需要多少步推理、多少次检索才能答对
- **多样性（Diversity）**：覆盖不同领域、推理类型、答案形式
- **可验证性（Verifiability）**：存在明确的正确答案，便于自动评估

## 3. Query 筛选：从海量问题中选出"好问题"

### 3.1 难度分级框架

最经典的框架来自 **FRAMES (Factuality, Retrieval, And reasoning MEasurement Set)**（Krishna et al., 2024）和后续工作：

| 难度级别 | 特征 | 例子 |
|---------|------|------|
| L1 - 单步事实 | 一次搜索直接回答 | "法国首都是哪里？" |
| L2 - 多步推理 | 需要 2-3 次搜索并整合 | "获得诺贝尔文学奖最多的国家的首都在哪个半球？" |
| L3 - 约束满足 | 多个条件需同时满足 | "找一个既是 G7 成员又人口少于 5000 万的国家" |
| L4 - 时序推理 | 涉及时间线变化 | "2010 年到 2020 年间 GDP 增速排名前三但人均 GDP 下降的国家" |
| L5 - 反直觉/对抗 | 答案违反常识预期 | "哪个沙漠国家的年降水量比伦敦还多？"（某些年份的特例） |

**Insight：** 真正有用的难题不是"信息量大"的题，而是"推理链长且链上每一步都可能出错"的题。

### 3.2 基于模型能力差的筛选（Model Gap Filtering）

**核心思想：** 一个好的难题 = 强模型能答对 + 弱模型答不对

```python
# 伪代码：Model Gap 筛选
def filter_by_model_gap(queries, strong_model, weak_model, threshold=0.3):
    selected = []
    for q in queries:
        score_strong = strong_model.evaluate(q)  # e.g., GPT-4 正确率
        score_weak = weak_model.evaluate(q)      # e.g., GPT-3.5 正确率
        gap = score_strong - score_weak
        if gap > threshold:
            selected.append(q)
    return selected
```

**为什么这有效？**
- Gap 大 → 说明这个问题需要高阶能力（推理、规划、验证）
- Gap 小且都对 → 问题太简单
- Gap 小且都错 → 问题可能有歧义或无解（需要人工检查）

**进阶做法（2025-2026 主流）：**
- 使用多个模型组成 **model committee**，取"多数模型答错但最强模型答对"的样本
- 引入 **搜索增强 vs 无搜索** 的 gap：同一个模型，有检索时答对、无检索时答错 → 该题适合训练 DeepSearch

### 3.3 多维度质量打分

来自 **Qwen-2.5 技术报告** 和 **DeepSeek-R1** 等工作的实践：

```
Quality Score = w1 × Difficulty + w2 × Clarity + w3 × Answerability 
             + w4 × SearchDependency + w5 × Novelty
```

各维度含义：

| 维度 | 怎么衡量 | 为什么重要 |
|------|---------|-----------|
| Difficulty | 模型需要几步推理（用 CoT 长度近似） | 筛掉太简单的 |
| Clarity | 问题是否无歧义（LLM-as-judge） | 保证可评估 |
| Answerability | 信息是否确实存在于公开网络 | 避免无解题 |
| SearchDependency | 不搜索能答对的概率有多低 | 确保题目真正需要搜索 |
| Novelty | 与已有数据集的语义距离 | 避免重复/过拟合 |

### 3.4 信息需求分类（Query Intent Taxonomy）

不同类型的搜索需求对 DeepSearch 的要求不同：

```
信息需求分类
├── 事实查询（Factoid）        → 测试检索精确度
├── 比较分析（Comparative）    → 测试多源整合
├── 因果推理（Causal）         → 测试逻辑链
├── 时序追踪（Temporal）       → 测试时间感知
├── 假设验证（Hypothesis）     → 测试批判性思维
└── 综合报告（Synthesis）      → 测试端到端深度搜索
```

**Insight：** 好的评估集应在这六个类别上均匀分布，而非全是事实查询。

## 4. 难题构造：如何"造"出有价值的难问题

### 4.1 组合式构造（Compositional Construction）

**思想：** 把多个简单事实"拼"成一个需要多步推理的复合问题。

**经典方法（MuSiQue, 2022 → 2025+ 改进版）：**

```
Step 1: 收集事实对
  - 事实A: "居里夫人出生在波兰华沙"
  - 事实B: "华沙是维斯瓦河上最大的城市"
  
Step 2: 通过共享实体（华沙）桥接
  → "居里夫人出生城市所在的河流是什么？"

Step 3: 继续叠加
  - 事实C: "维斯瓦河全长 1,047 公里"
  → "居里夫人出生城市所在河流的长度是多少公里？"
```

**2025+ 改进：**
- **自动化桥接**：用知识图谱自动发现可连接的实体路径
- **质量过滤**：生成后用 LLM 判断"这个组合问题是否自然"（避免生硬拼凑）
- **答案唯一性验证**：确保组合后答案仍然唯一确定

### 4.2 约束叠加法（Constraint Stacking）

**思想：** 从一个简单问题出发，不断添加约束条件，直到难度达标。

```
Level 0: "推荐一部科幻电影"
  ↓ +约束: 时间
Level 1: "推荐一部 2020 年之后的科幻电影"
  ↓ +约束: 评分
Level 2: "推荐一部 2020 年之后、IMDB 评分 8.0 以上的科幻电影"
  ↓ +约束: 特定元素
Level 3: "推荐一部 2020 年后、IMDB 8.0+、涉及时间旅行、且非英语的科幻电影"
  ↓ +约束: 排除
Level 4: "...且不是由流媒体平台首发的"
```

**关键 Insight：**
- 每加一层约束，搜索空间指数缩小，答案变得更难找
- 约束之间要**互相兼容**（否则无解）→ 需要预先验证
- 最好的约束是"需要查不同来源才能验证"的

### 4.3 对抗式生成（Adversarial Generation）

**核心框架（源自 Dynabench → 适配到 DeepSearch 场景）：**

```
┌──────────────┐     生成候选难题      ┌──────────────┐
│  Red Team    │ ───────────────────→ │  DeepSearch  │
│  (攻击者LLM) │ ←─────────────────── │  (防御者)     │
└──────────────┘     尝试回答         └──────────────┘
        │                                    │
        │  防御者答对 → 难度不够，继续进化       │
        │  防御者答错 → 记录为有效难题          │
        ▼                                    ▼
   ┌──────────┐                        ┌──────────┐
   │ 难题池   │                         │ 训练集   │
   └──────────┘                        └──────────┘
```

**三种对抗策略：**

| 策略 | 方法 | 适用场景 |
|------|------|---------|
| 事实扰动 | 在真实事实附近构造"差一点就对"的陷阱 | 测试精确性 |
| 推理陷阱 | 让表面推理链得到错误答案 | 测试深度推理 |
| 检索误导 | 问题中包含高频但无关的关键词 | 测试检索策略 |

**2025-2026 最新做法（来自 OpenAI、Anthropic 等公开报告）：**
- 用 **强模型当 Red Team**（如 Claude/GPT-4 级别），专门给目标 DeepSearch 系统出难题
- 引入 **迭代对抗**：每轮收集系统答错的题，分析错误模式，下一轮针对性出题
- **AutoRedTeam 框架**：完全自动化的红蓝对抗循环

### 4.4 基于知识图谱的多跳推理

**方法论：**

```
知识图谱 (KG)
    │
    ▼
选择起始实体 (e.g., "Albert Einstein")
    │
    ▼
沿关系路径随机游走 N 步
    路径: Einstein → born_in → Ulm → located_in → Baden-Württemberg → capital → Stuttgart
    │
    ▼
将路径转化为自然语言问题
    "爱因斯坦出生城市所在州的首府是哪里？"
    │
    ▼
验证：(1) 答案唯一？ (2) 需要 N 步检索？ (3) 无捷径？
```

**"无捷径"验证是关键：**
- 如果问题可以通过直接搜索答案（跳过中间步骤）得到，那它不是真正的多跳题
- 验证方法：删除中间实体后，模型还能答对吗？如果能 → 假多跳，丢弃

**进阶：条件约束路径**
- 不是随机游走，而是带条件的路径（如"人口最多的"、"成立最早的"）
- 每个条件都需要独立验证 → 真正迫使系统做多次检索

### 4.5 进化式难度提升（Evolutionary Approach）

**灵感来源：** WizardLM 的 Evol-Instruct → 适配到搜索场景

```
初始种子题: "谁发明了电话？"
     │
     ├── 深化 (Deepening): "贝尔发明电话的专利号是什么？专利提交日期和正式通过日期相差几天？"
     │
     ├── 宽化 (Broadening): "在贝尔之前，还有哪些人声称发明了电话？他们各自的方案有何不同？"
     │
     ├── 条件化 (Conditioning): "如果只考虑美国专利局的记录，谁是电话的法定第一发明人？"
     │
     └── 反转 (Reversing): "电话发明归属争议中，哪位竞争者最终在 2002 年被美国国会承认？"
```

**进化质量控制：**
- 每次进化后，检查问题是否仍有明确答案
- 计算进化前后的 model gap 是否增大
- 人工抽检进化链的逻辑连贯性

## 5. 代表性工作详解

### 5.1 FRAMES（Google, 2024）

**核心贡献：** 专门为 RAG 系统设计的多维度难度评估集

- 人工标注的多跳推理问题
- 每题标注：需要检索的文档数、推理步数、答案类型
- **关键发现：** 随着推理步数增加，即使最强模型的准确率也急剧下降
- 论文链接：搜索 "FRAMES Google Research 2024 RAG benchmark"

### 5.2 Humanity's Last Exam (HLE, 2025)

**核心贡献：** 众包来自各领域专家的"人类最后考试题"

- 由 Center for AI Safety (CAIS) 联合 Scale AI 等多家机构发起
- 筛选标准：问题必须让 GPT-4/Claude 答错，但领域专家能答对
- **Insight：** 最有效的难题来自"需要领域深度知识 + 跨领域连接"的交叉地带
- DeepSearch 相关：很多 HLE 题理论上可以通过足够深度的搜索解决

### 5.3 Agentic Search 评估思路（2025+ 趋势）

**核心思想：** 将搜索过程建模为 Agent 决策序列，不只评估最终答案

- 评估维度包括**搜索策略质量**（是否高效、是否有不必要的冗余步骤）
- 难题标准：最优搜索策略非 trivial（需要回溯、重新规划、修正查询）
- 衍生指标：**Search Trace Complexity** — 最短正确搜索路径的步数
- 代表方向：WebArena（CMU, 2024）对 web agent 的评估、以及各 DeepSearch 系统内部的 trace-level 评测
- ⚠️ 注：这是一个活跃的研究方向，尚无单一标准化论文，需自行追踪最新工作

### 5.4 自动化 Benchmark 生成 Pipeline（2025-2026 趋势）

**核心思路：** 用 LLM 自动化 benchmark 的生成-筛选-验证全流程，减少人工成本

典型 pipeline 结构（综合多家实践）：

```
自动化 Benchmark 生成 Pipeline:
1. 从真实用户 query 日志 / 知识图谱中采样种子
2. LLM-as-judge 多维打分筛选
3. 对抗式进化提升难度（Evol-Instruct 风格）
4. 自动验证答案正确性（多模型一致性投票）
5. 去重 + 多样性采样（embedding 聚类）
6. 人工最终验审（仅对自动pipeline无法确定的样本）
```

代表工作：
- **Auto-J** (2023): LLM-as-judge 自动评估
- **Self-Instruct → Evol-Instruct** 系列: 自动生成+进化指令
- 各公司内部的 data flywheel pipeline（思路类似，细节不公开）
- ⚠️ "AutoBencher" 不是某篇论文的固定名称，而是这类方法的泛称

### 5.5 Open Deep Research Benchmarks（2025-2026 社区工作）

| Benchmark | 特点 | 题量 | 难度 |
|-----------|------|------|------|
| BrowseComp (OpenAI) | 需要深度浏览才能找到的事实 | 1,000+ | 极高 |

## 6. 评估：如何验证你的筛选/构造是有效的

### 6.1 好的难题应满足的四个条件

```
                    ┌─────────────┐
                    │   好的难题   │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           │               │               │
     ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
     │ 确实难    │  │ 有明确答案 │  │ 需要搜索   │
     │(模型答错) │  │(可自动评估)│  │(非纯推理)  │
     └───────────┘  └───────────┘  └───────────┘
                           │
                    ┌─────▼─────┐
                    │ 不是人为   │
                    │ 不自然的   │
                    └───────────┘
```

### 6.2 量化评估方法

**方法 1：模型 Pass Rate 曲线**
```
好的难度分布应呈现：
- 最强模型 (frontier): 40-70% 通过率
- 中等模型: 15-35% 通过率  
- 弱模型: 0-10% 通过率

如果最强模型也只有 <20%：题目可能有问题（太难/有歧义）
如果弱模型也有 >50%：不够难
```

**方法 2：搜索依赖度验证**
```python
# 对每道题，比较有搜索和无搜索的表现差
search_dependency = accuracy_with_search - accuracy_without_search
# 好的 DeepSearch 难题: search_dependency > 0.3
```

**方法 3：人工一致性检验（Inter-annotator Agreement）**
- 至少 3 名标注者独立作答
- 一致性 > 0.8 → 问题清晰，答案明确
- 一致性 < 0.5 → 可能有歧义，需修改或丢弃

## 7. 实践建议与 Pitfall

### 7.1 常见坑

| 坑 | 表现 | 解决方案 |
|----|------|---------|
| 假多跳 | 看似需要多步，但一次搜索就能答 | 用"删除中间实体"法验证 |
| 时效过期 | 答案随时间变化但标注是静态的 | 标注时记录时间戳 + 定期刷新 |
| 领域偏见 | 全是某一类题（如地理题） | 使用多样性采样策略 |
| 难度通胀 | 模型升级后原来的难题变简单 | 定期用最新模型重新评估 |
| 答案泄露 | 训练集中包含了评估题的答案 | 使用时效性题目或全新构造题 |

### 7.2 推荐的工作流程

```
1. 确定目标
   └─ 训练用？评估用？领域是什么？
   
2. 种子收集
   └─ 用户日志 / 知识图谱 / 现有数据集改写
   
3. 难度提升（选 1-2 种方法组合）
   └─ 组合式 + 约束叠加 效果稳定
   └─ 对抗式 效果最好但成本高
   
4. 质量验证
   └─ Model Gap > 0.3
   └─ Search Dependency > 0.3
   └─ 答案唯一性通过
   
5. 多样性采样
   └─ 在通过验证的候选中，按类别均匀采样
   
6. 人工审核
   └─ 抽样 10-20% 进行专家复核
```

### 7.3 写论文 / 做项目时的建议

- **不要只追求难度数字**，一个模型全错的 benchmark 没有区分度
- **Report 完整的 pass rate 分布**，而非只报告平均值
- **开源你的筛选 pipeline**，而非只开源最终数据集
- **版本化你的 benchmark**——模型在进步，benchmark 也应该进化
