## 问题

一个 Agent 循环执行 50 轮工具调用，每轮的完整返回结果都堆在 context 里。到后面模型开始"忘事"、重复调用、忽略早期约束。有哪些工程手段？

## 一句话回答

**别把 context 当数据库用。** 工具结果应该被压缩成结论、状态应该外置到文件或数据库，context 只保留"当前决策需要的信息"。

## 展开

### 1. 先看它为什么坏

两个独立的问题被混在一起：

- **容量问题** —— 塞不下，超出窗口被截断
- **注意力问题** —— 塞得下但模型找不到重点（*lost in the middle*，中间部分的信息利用率显著低于首尾）

即便有 1M 窗口，**长不等于好用**：噪声会增加、延迟和成本线性上涨、模型对中段信息的召回率下降。

### 2. 手段一：工具结果分级处理

不要所有结果一视同仁。按体积和用途分流：

| 结果类型 | 处理方式 |
|---------|---------|
| 小结果（< 500 token） | 原样保留 |
| 大结果（日志、文件内容） | **落盘**，context 里只留路径 + 摘要 |
| 检索结果 | 只留命中的片段 + 出处，别塞整篇文档 |
| 报错信息 | 保留，但截断堆栈，只留关键帧 |

核心动作：**把"内容"变成"引用"**。模型需要时再按需读取 —— 这就是 Agent 版的虚拟内存。

### 3. 手段二：历史压缩

- **滑动窗口** —— 只留最近 N 轮。简单，但会丢早期约束
- **摘要压缩** —— 定期把历史总结成一段话。注意：**摘要会丢细节**，关键约束要单独固定
- **固定区 + 滚动区** —— 系统提示、任务目标、关键约束永远留在最前面（避开中段效应），历史在滚动区压缩

实践中 **固定区 + 摘要** 组合最稳。

### 4. 手段三：Subagent 隔离

这是最被低估的一招。把"脏活"丢给子 Agent：

```
主 Agent（干净的短上下文，负责决策）
   ├── 子 Agent A：读完 20 个文件，只返回结论
   ├── 子 Agent B：跑完测试，只返回失败用例
   └── 子 Agent C：搜了 50 条资料，只返回摘要
```

子 Agent 消化大量内容，返回**结构化结论**。主 Agent 的上下文始终保持干净。

代价是：额外的调用开销、信息在传递中可能失真。

### 5. 手段四：状态外置

Agent 的长期状态不该在 context 里，应该在：

- **文件系统** —— 计划文件、进度文件（模型每次读最新的）
- **数据库 / KV** —— 会话状态、已完成的子任务
- **结构化记忆** —— 明确区分"事实"和"推测"

判断标准很简单：**如果一个信息跨轮次还需要精确存在，它就不该只活在 context 里。**

### 6. 手段五：Prompt Caching

不改内容，改**成本**。把固定的长前缀（系统提示、工具定义、示例）标记为可缓存，后续轮次复用 KV，只对新增部分计算。

在 Agent 场景收益巨大 —— 工具定义动辄几千 token，且每轮都重复。

**注意**：前缀里任何一处改动都会让缓存失效。别在系统提示里塞时间戳。

## 面试延伸

- **如果摘要丢掉了关键约束怎么办？** 关键约束不该进摘要流程，应放在固定区，永不压缩
- **怎么判断该压缩还是该外置？** 看跨轮次是否需要精确值 —— 需要就外置，只需要大意就压缩
- **Prompt Cache 和上下文压缩冲突吗？** 不冲突但要小心：压缩会改写历史，可能导致缓存失效，通常只缓存固定前缀
