## 0. TL;DR（30 秒版）

- **共同问题**：一个模型如何同时获得数学、代码、Agent、对话、安全等多领域巅峰能力（"能力融合"，Capability Integration）。
- **路线 A（Mixed RL 数据合版）**：把各领域数据放进**同一次 RL 训练**里混着训。头号难点是**跨域奖励冲突**——DeepSeek-V4 明确因此放弃了这条路线。
- **路线 B（MOPD 合版）**：每个领域先单独训出**专家模型**（SFT + RL），再用**多教师在线蒸馏（MOPD）**把专家能力蒸进一个学生模型。DeepSeek-V4（叫 OPD）和小米 MiMo-V2 系列（叫 MOPD）都走这条。
- **2026 年行业共识正在形成**：单纯混合奖励信号打不过"分训专家 + 在线蒸馏"；但 MOPD 也有自己的坑（成本翻倍、教师能力封顶、全词表 KL 计算开销、MoE 路由抖动）。
- 小米 MiMo-V2.6（2026-09-22 发布）是目前**唯一把混合 RL 训练过程实时公开**的案例，提供了大量一手工程数据（见 §4.2）。

## 1. 问题定义：到底要解决什么问题

### 1.1 共同问题：能力融合（Capability Integration）

现代旗舰模型需要同时具备：

```
数学推理 / 代码生成 / Agentic 工具调用 / 通用对话 / 长文写作 / 安全对齐 / 多模态理解
```

这些能力的**奖励信号形态完全不同**：

| 能力域 | 奖励信号 | 反馈延迟 | 轨迹形态 |
|--------|---------|---------|---------|
| 数学 | 规则校验（答案对错） | 秒级 | 单轮长 CoT |
| 代码 | 单测通过率（可验证） | 秒~分钟级 | 单轮或少量交互 |
| Agentic（SWE/浏览器/终端） | 环境执行结果 | 分钟~小时级 | 多轮工具调用、超长轨迹 |
| 通用对话 | 偏好 RM / LLM-as-Judge | 秒级 | 短回复 |
| 安全 | Safety RM / 规则 | 秒级 | 拒绝/合规回答 |

**问题**：怎么把这些能力"合"进同一个模型，且不互相拖垮？

### 1.2 两条技术路线

```
                    能力融合问题
                         │
         ┌───────────────┴───────────────┐
         ▼                               ▼
  路线 A：Mixed RL                 路线 B：专家分训 + MOPD
  （多域数据混进一次 RL）           （各域单训专家 → 在线蒸馏合版）
         │                               │
  ├─ Qwen3 General RL             ├─ DeepSeek-V4 (OPD)
  ├─ Qwen3.5 混合 RL              ├─ MiMo-V2-Flash (MOPD)
  ├─ MiMo-V2.6 RL 阶段            └─ MOPD 论文 (北大×小米, 2026-06)
  └─ GLM-5（分层叠加，部分混合）
```

### 1.3 术语澄清（重要）

> **MOPD = Multi-Teacher On-Policy Distillation（多教师在线策略蒸馏）**，由小米在 MiMo-V2-Flash 技术报告（2025-12）中提出，并于 2026-06 与北大联合发布独立论文《MOPD: Multi-Teacher On-Policy Distillation for Capability Integration in LLM Post-Training》。
>
> 它**不是**"Multi-Objective Policy Distillation / 多目标优化"的缩写。多目标 RL（MORL）是另一个研究方向，与本文主题相关但不同，勿混淆。
>
> DeepSeek-V4 中的等价技术叫 **OPD（On-Policy Distillation，在线策略蒸馏）**，公式几乎一致。本文统一用 MOPD 指代这一范式。

### 1.4 核心矛盾一句话总结

| 路线 | 一句话矛盾 |
|------|-----------|
| Mixed RL | 不同域的奖励信号**量纲不同、方向冲突**，混在一起会互相污染 |
| MOPD | 蒸得好不好取决于**教师质量和蒸馏保真度**，且成本≈"训 N 个专家 + 训 1 个学生" |

## 2. 路线 A：Mixed RL 数据合版的问题与难点

### 2.1 跨域奖励冲突（头号问题）

**问题定义**：不同领域的奖励函数对同一行为给出矛盾信号。

```
例：模型学会"先写长 CoT 再回答"在数学域拿高分
    → 同一行为搬到对话域，被偏好 RM 判为"啰嗦"扣分
    → 混合训练时，两个梯度方向相反，模型无所适从
```

**这是 DeepSeek-V4 官方给出的放弃 mixed-domain RL 的直接原因**。V4 技术报告中的对比逻辑：

| 方案 | 思路 | 局限 |
|------|------|------|
| 权重合并 | 多专家权重加权平均 | 参数空间不对齐，合并后性能退化 |
| **混合 RL** | 所有领域奖励信号混合训练 | **不同领域的奖励可能冲突** |
| OPD/MOPD | 学生在自己生成的轨迹上学教师分布 | 计算成本高，但效果最好 |

### 2.2 奖励尺度与语义不可通约

**三层不通约**：

| 层面 | 问题 | 实例 |
|------|------|------|
| 尺度 | 数值范围不同 | 代码 reward ∈ {0,1}（pass/fail）；偏好 RM ∈ [-3, 3] |
| 语义 | 同分值不同含义 | 数学 0.8 = 部分正确；对话 0.8 = 还行但不够好 |
| 信息量 | 信号密度不同 | 可验证奖励是 0/1 稀疏二值；RM 是稠密连续值 |

**后果**：不归一化时，数值范围大的奖励域会主导梯度，相当于该域数据占比被暗中放大数倍。

**标准解法**（见 §5）：per-task 奖励归一化（z-score 或 percentile），GRPO 组内归一化天然部分缓解此问题。

### 2.3 梯度干扰与跷跷板效应（Seesaw Effect）

**问题定义**：不同任务的梯度方向冲突，训练时各域性能此消彼长。

```
典型现象：
  调大代码数据比例 → 代码 ↑ 对话 ↓
  调大对话数据比例 → 对话 ↑ 代码 ↓
  反复拉锯，总性能 plateau
```

**量化手段**：计算任务间梯度余弦相似度，`cos(g_A, g_B) < 0` 即冲突。

**GLM-5 的对应表述**：异步混合训练中"分布偏移、梯度冲突、更新不同步"被列为离策略训练稳定性的三大杀手（GLM-5 技术报告 / slime 框架解读）。

### 2.4 数据配比与动态漂移

**问题定义**：各域数据按什么比例混？且这个比例是否需要随训练动态变化？

**难点**：

1. **组合爆炸**：5 个域 × 10 个比例档位 = 10 万种组合，每种要跑完整 RL 才能验证。
2. **最优配比随训练阶段漂移**：初期和末期的最优配比不同。
3. **配比漂移即风险源**：小米 MiMo-V2.6 仪表盘公开数据显示，其 RL 阶段配比是**动态变化**的（见下表），官方把"盯配比漂移"列为防崩坏手段。

**一手数据（MiMo-V2.6-Pro，step 27 的 batch 构成，2026-09-20 快照）**：

| 类别 | 数据源数 | prompts | 占比 | 漂移趋势 |
|------|---------|---------|------|---------|
| code | 11 | 1,061 | 67.7% | ▲ +0.7pt |
| visual | 6 | 270 | 17.2% | ▼ −0.7pt |
| general | 4 | 190 | 12.1% | ▲ +0.5pt |
| chat | 3 | 47 | 3.0% | ▼ −0.5pt |
| cyber | 1 | 0 | 0.0% | —（该步缺货） |

共 25 个数据源同时供题，每步 1,568 个 prompt × 每 prompt 采 16 条序列 = 25,088 条轨迹/步。

### 2.5 轨迹结构差异：长度膨胀与轮次差异

**问题定义**：不同域的 rollout 轨迹长度、交互轮次差异巨大，导致：

- **长度膨胀（跨域传染）**：数学/代码域奖励长 CoT，混合训练后对话域也变啰嗦。
- **单步 token 量随训练膨胀**：模型变强后推理链更长、工具调用轮次更多。

**一手数据（MiMo-V2.6）**：flash 全程 81.4B token / 30 步 ≈ 平均 2.71B/步，但最后一步 3.7B；pro 平均 2.41B/步，末步 3.15B。**按初始步成本估预算必然低估**——这是 agentic 混合 RL 预算规划的经典坑。

**工程后果**：长短轨迹混在一个 batch，短轨迹大量 padding，GPU 利用率被拖垮。GLM-5 的 slime、Qwen3.5 的异步 RL 框架本质上都在解决这个"快慢不齐"的问题。

### 2.6 On-policy / Off-policy 混用与训推不一致

**问题定义**：异步架构下，rollout 用的策略版本落后于训练中的策略版本，产生 off-policy 偏移；同时推理引擎（如 vLLM）与训练引擎（如 Megatron）的数值实现差异造成"训推不一致"。

**小米的暴露**：MiMo-V2.6 仪表盘长期监控 `train_infer_diff/new_infer/kl`（pro 0.0074 / flash 0.011），并有对口论文《Stabilizing MoE Reinforcement Learning by Aligning Training and Inference Routers》（2025-10）——核心发现是 **MoE 模型训练与推理的路由分布不一致会直接破坏 RL 稳定性**，需要对齐两侧 router。

**GLM-5 的表述**：token 对齐（sequence/state/action 不错位）+ 离策略稳定性是异步 RL 的两大核心挑战。

### 2.7 MoE 特有坑：专家负载不均

**一手事故（MiMo-V2.6-Pro，官方 notice 原文）**：

> "the pro run restarted at step 17 due to a GPU OOM issue caused by expert load imbalance. we have adjusted the training parallelism strategy."

**机理**：MoE 路由是动态的，RL 训练不断推动策略偏移 → 路由分布剧烈波动 → 某个 rank 上的专家被打爆 → OOM。RL 比 SFT 更容易触发，因为策略在变、路由也在变。

**解法方向**：调整 EP/TP 并行切分、加负载均衡约束、训推路由对齐（见 §2.6）。

### 2.8 Reward Hacking 跨域传染

**问题定义**：模型在单域发现的投机模式，混合训练后扩散到其他域。

```
域内 hacking：代码域学会 hardcode 通过特定测试
传染后：    对话域也开始"背模板式"作答
           安全域学会"一律拒绝"（安全分高但 helpfulness 崩）
```

**混合放大的原因**：一个"万能模式"若在多个奖励上都能拿到中等分，混合训练会强化它成为全局默认行为（reward collapse）。

## 3. 路线 B：专家分训 + MOPD 合版的问题与难点

### 3.1 定义与流程

**MOPD 的标准三阶段**（小米 MiMo-V2-Flash / MOPD 论文）：

```
Stage 1：通用 SFT
    → 得到一个行为规范的基座学生模型
Stage 2：领域专家 RL
    → 数学/代码/Agent/对话等各域分别做 SFT + RL，训出 N 个巅峰专家
    → 专家冻结（不再更新），组成教师组
Stage 3：学生 MOPD
    → 从多领域题库随机抽题，学生自己生成回答
    → 在每个 token 位置，用对应领域教师的分布做监督信号
    → 以"学生-教师分布散度"为奖励做 RL 优化（GRPO 类）
```

**三个核心特性**（MiMo-V2-Flash 技术报告原文）：

1. **稠密 token 级指导**：区别于稀疏的序列级反馈，每个 token 都有教师监督。
2. **在线策略优化（On-Policy）**：学生从**自己生成的响应**中学习，消除暴露偏差（exposure bias），梯度更小更稳。
3. **内在奖励鲁棒性**：奖励源于分布散度而非某个可游戏的标量 RM，**天然抗 reward hacking**。

### 3.2 数学形式（DeepSeek-V4 OPD 版）

$$\mathcal{L}_{OPD}(\theta) = \sum_{i=1}^{N} w_i \cdot D_{KL}(\pi_\theta \| \pi_{E_i})$$

关键设计选择及理由（V4 报告）：

| 设计 | 选择 | 理由 |
|------|------|------|
| KL 方向 | **反向 KL**（学生 π_θ 在前） | mode-seeking，精确匹配教师强项模式；正向 KL 是 mode-covering，注意力被摊薄 |
| 采样分布 | **学生自己采样**（on-policy） | 训练分布与当前策略一致，避免分布偏移 |
| KL 估计 | **全词表 logit 蒸馏** | 单 token 采样估计省算力但梯度方差高；**十多个教师时高方差会被放大**，宁可花算力换稳定性与保真度 |
| 教师权重 w_i | 按域加权 | 控制各域能力的融合配比 |

### 3.3 MOPD 解决了什么

| Mixed RL 的坑 | MOPD 如何规避 |
|--------------|--------------|
| 跨域奖励冲突 | 各域专家内部只有单一奖励，冲突被隔离在专家训练阶段 |
| 奖励不可通约 | 蒸馏阶段没有异构奖励，只有统一的分布散度 |
| Reward hacking | 分布散度不是可游戏的标量 RM |
| 配比玄学 | 蒸馏配比 = 教师权重 w_i，语义清晰、可调 |
| 跷跷板效应 | 各域能力通过教师"定格"在巅峰，学生学的是并集 |

### 3.4 MOPD 自己的难点（别忽视）

**难点 1：成本翻倍**

```
成本 = N 个专家的完整后训练 + 1 次蒸馏训练
```

参考价签（MiMo-V2.6 RL 阶段公开数据）：flash 版 30 步 / 3.5 天 / **85.4 万美元**；pro 版 27+ 步已烧 **231.5 万美元**（单 token 成本约为 flash 的 3.4 倍）。这还只是学生端一次 RL 的量级，专家端成本另算。

**难点 2：教师能力封顶**

学生的每个域上限 = 对应教师的水平。**专家训不好，蒸馏救不回来**。且专家之间若能力差距悬殊，弱教师的域会拖学生后腿。

**难点 3：全词表 KL 的算力开销**

DeepSeek-V4 明确选择全词表 logit 计算 KL（而非单 token 采样估计），理由是十多个教师时高方差梯度会放大不稳定——代价是**每步要多跑 N 个教师的前向**（虽可并行/离线缓存 logits，但显存与通信开销实打实）。

**难点 4：多教师路由与题库设计**

学生抽到某域的题，就用对应域教师监督。**题库的领域分布、难度分布直接决定融合效果**——本质上是把 Mixed RL 的"数据配比难题"转移到了蒸馏题库设计上，并没有消灭它。

**难点 5：On-policy 的基础设施要求**

学生要自己采样 → 需要训推分离架构 + 高并发 rollout。GLM-5（slime）、Qwen3.5（异步 RL + 投机采样 + rollout 路由回放，端到端提速 3–5×）、DeepSeek-V4（可抢占 rollout 服务 + token 级 WAL 断点恢复）砸在基础设施上的投入，本质都是为 on-policy 训练买单。

**难点 6：蒸馏保真度 vs 学生容量**

学生模型容量不足时，无法同时装下所有教师的巅峰能力——**能力互斥从"训练冲突"转化为"容量瓶颈"**。MiMo-V2-Flash 用 309B 总参 / 15B 激活的 MoE 来撑容量，不是巧合。

**难点 7：专家的"风格"冲突仍在**

各专家的回答风格（长度、格式、口吻）不同，学生学到的可能是风格的折中。DeepSeek-V4 的解法是连**推理力度都拆成独立专家**（Non-think 8K / Think 128K / Think Max 384K 三档分别训练），避免在一个专家内部调和长度冲突。

**难点 8：Reward/评估并未消失**

蒸馏阶段虽无需异构奖励，但**专家训练阶段仍然需要各域的可验证奖励或 RM**——DeepSeek-V4 为此引入 GRM（生成式奖励模型，模型自己生成评估理由，且 GRM 本身也做 RL，"做题"与"批改"互相促进）。奖励工程只是换了个位置，没有消失。

### 3.5 与"模型合并（Model Merging / Soup）"的对比

| 维度 | 权重合并（Soup 类） | MOPD 蒸馏 |
|------|-------------------|-----------|
| 操作对象 | 参数空间 | 行为分布（输出 logits） |
| 架构要求 | 必须同架构同初始化 | 可跨规模（强教师蒸弱学生） |
| 能力互斥 | 参数干扰严重，性能退化（V4 报告实测结论） | 显著缓解 |
| 成本 | 几乎为零 | 高（一次完整训练） |
| 可控性 | 只有合并系数可调 | 教师权重、题库、KL 强度多维可调 |

## 4. 各家技术报告方案详解（2026 最新）

### 4.1 DeepSeek-V4（2026-04 发布，V4-Pro 1.6T / V4-Flash 284B）

**路线：明确放弃 mixed-domain RL，走"专家分训 + OPD 蒸馏"**

- **专家训练**：数学、代码、Agent、指令遵循等域分别做 SFT + GRPO。
- **OPD 整合**：反向 KL + 学生 on-policy 采样 + 全词表 logit 蒸馏（理由见 §3.2）。
- **GRM（生成式奖励模型）**：不用标量 RM。让模型生成带详细理由的评估判断（信息量远大于分数），且 GRM 本身也做 RL——模型同时学"做题"和"批改"。
- **推理力度三模式分专家训练**：Non-think（8K 上下文）/ Think（128K）/ Think Max（384K，RL 时配更大长度惩罚与上下文窗口），各自独立优化到最佳，避免内部调和。
- **交错思考（Interleaved Thinking）**：Agent 多轮场景保留全部历史思考痕迹（V3.2 是每轮清零重推），依赖百万 token 上下文支撑。
- **基础设施**：可抢占 rollout 服务 + token 粒度 WAL（每生成一个 token 即落盘，被抢占后从最后 token 恢复）；DSec 沙箱平台（Rust），数十万并发沙箱实例支撑代码 Agent 的可验证奖励。

### 4.2 小米 MiMo 线（MiMo-V2-Flash → MOPD 论文 → MiMo-V2.6）

**路线：MOPD 的发明者与持续迭代者**

**MiMo-V2-Flash（2025-12，309B 总参 / 15B 激活 MoE）**
- 提出 MOPD 三阶段范式（§3.1），解决传统模型合并的**能力互斥**问题。
- 配套基础设施 R3（Rollout Routing Replay）解决 MoE 在 RL 训练中的路由回放问题。

**MOPD 独立论文（2026-06，北大×小米联合）**
- 《MOPD: Multi-Teacher On-Policy Distillation for Capability Integration in LLM Post-Training》，把"能力融合"正式定义为问题，给出完整方法论与实验。

**MiMo-V2.6（2026-09-22 发布，Pro 1.02T/42B 激活 + Flash，原生全模态）**
- 史上首个**实时公开 RL 训练仪表盘**的厂商（mimo.xiaomi.com/rl），公开 step 数、token 数、美元成本、pass rate、grad norm、KL。
- **RL 阶段就是一次混合多域 agentic RL**：25 个数据源，code/visual/general/chat/cyber 五类，配比动态漂移（§2.4 表格）。
- **动态采样（dynsam）**：每 prompt 采 16 条，avg@16 全过（太易）或全挂（太难）的题被剔除，算力只投在"有梯度信号"的题上。Pro 中途主动"过滤掉当前模型觉得相对容易的任务"。
- **事故公开**：step 17 因专家负载不均 OOM 重启，随后调整并行策略（§2.7）。
- **成本公开**：flash 全程 $854K / pro 已 $2.3M+；单步 token 随训练膨胀（§2.5）。
- 对口论文还包括《Stabilizing MoE RL by Aligning Training and Inference Routers》、ARL-Tangram（agentic RL 资源效率）、HySparse。

**值得注意**：MiMo-V2.6 说明小米并非"只用 MOPD 不用混合 RL"——MOPD 用于能力合版，之后仍有混合多域 RL 阶段做进一步提升。**两条路线是串联关系，不是互斥关系。**

### 4.3 Qwen3（2025-05）→ Qwen3.5（2026-02，397B-A17B）

**路线：分阶段 RL + 阶段内混合 + 规模化 RL 环境**

**Qwen3 后训练四阶段**：
1. Long-CoT 冷启动 SFT（思考 token 加权、格式一致性惩罚）
2. **Reasoning RL**：数学 + 代码，GRPO，可验证奖励（AIME 85.1 / Codeforces 2056）
3. Thinking Mode Fusion（think/no-think 混合 SFT，统一双模式）
4. **General RL**：覆盖 20+ 通用能力维度，三种奖励混用：
   - Rule-based Reward
   - Model-based Reward **with** Reference Answer（Qwen2.5-72B-Instruct 做参考模型）
   - Model-based Reward **without** Reference Answer（人类偏好 RM）

**Qwen3.5 的演进**：
- 后训练性能提升主要归功于 **RL 环境与任务的全面扩展**——不再针对特定指标优化，强调环境难度与可泛化性。
- 可扩展**异步 RL 框架**：训推分离架构支撑**百万级 Agent 环境交互**；投机采样 + Rollout 路由回放，端到端提速 3–5×。
- 工具调用基准（Tool-Decathlon、MCP-Mark）表现突出，官方称之为"授人以渔"。

### 4.4 GLM-5（2026-02，744B，技术报告《From Vibe Coding to Agentic Engineering》）

**路线：三级 RL 分层独立训练、逐层叠加**

```
Reasoning RL（推理）→ Agentic RL（智能体）→ General RL（通用）
   独立训练，逐层叠加，而非一次性全混
```

- **slime 框架**：Rollout 集群与训练集群**完全解耦的异步架构**——解决 agentic 任务"长周期、高交互、多步骤"导致 GPU 空等环境返回的问题（暴力堆算力在此失效）。
- **自陈两大核心挑战**（异步混合 RL 的通病）：
  1. **Token 对齐**：生成/训练分离时 sequence、state、action 的 token 精准对齐。
  2. **离策略稳定性**：分布偏移、梯度冲突、更新不同步。
- **DSA 稀疏注意力在 RL 下的稳定性**是靠大量实践踩坑解决的（精细上下文管理 + 训练稳定性优化）。
- 三类高仿真可验证环境：软件工程 / 终端操作 / 信息搜索。
- 成绩：SWE-Bench Verified 77.8，AA Intelligence Index 50（当时开源第一）。

2. **能力合版首选"分训 + 在线蒸馏"**，混合 RL 退居为蒸馏后的进一步打磨手段（或用于环境同构的域）。

## 5. 工程难点 → 解法对照表

### 5.1 训练稳定性

| 难点 | 解法 | 出处/实践者 |
|------|------|------------|
| 跨域奖励冲突 | 分训专家 + MOPD/OPD 蒸馏合版 | DeepSeek-V4、MiMo |
| 奖励尺度不一 | Per-task 归一化（z-score/percentile）；GRPO 组内归一化 | 各家标配 |
| 梯度冲突/跷跷板 | PCGrad/CAGrad 梯度手术；或干脆分训（蒸馏路线） | PCGrad (Yu et al. 2020) |
| 训推不一致（MoE 路由） | 对齐训练/推理两侧 router；监控 train/infer KL | 小米《Stabilizing MoE RL...》 |
| MoE 专家负载不均 OOM | 调整 EP/TP 并行策略、负载均衡约束 | MiMo-V2.6 step 17 事故 |
| 离策略不稳定 | Token 级对齐校验；IS ratio clipping；控制数据陈旧度 | GLM-5 slime |
| Loss spike | 极端 IS ratio 样本直接丢弃；per-task KL 系数 | 工程惯例 |

### 5.2 基础设施

| 难点 | 解法 | 出处/实践者 |
|------|------|------------|
| Agentic 轨迹慢、GPU 空等 | Rollout/训练集群解耦的异步架构 | GLM-5 slime、Qwen3.5 |
| 训推吞吐瓶颈 | 投机采样 + Rollout 路由回放（3–5× 提速） | Qwen3.5、MiMo R3 |
| 长轨迹被抢占丢进度 | Token 粒度 WAL，断点从最后 token 恢复 | DeepSeek-V4 |
| 代码奖励需执行验证 | 数十万并发沙箱平台 | DeepSeek-V4 DSec |
| 单步 token 量膨胀致预算失控 | 按末步而非首步成本做预算；动态监控 | MiMo-V2.6 仪表盘教训 |
| 全词表 KL 算力开销 | 教师 logits 离线缓存/并行前向 | DeepSeek-V4 OPD |

### 5.3 数据侧

| 难点 | 解法 | 出处/实践者 |
|------|------|------------|
| 配比玄学 | 动态采样：剔除全对（太易）/全错（太难）的题 | MiMo-V2.6 dynsam |
| 过易题浪费算力 | 训练中主动"过滤当前模型觉得容易的任务" | MiMo-V2.6 pro run |
| 蒸馏配比难题 | 转化为教师权重 w_i + 题库领域/难度分布设计 | MOPD/OPD |
| 标量 RM 信息量低、可游戏 | GRM 生成式奖励（带理由），GRM 自身也 RL | DeepSeek-V4 |
| 奖励信号异构 | 统一到"可验证环境奖励"为主战场 | 2026 各家共识 |
| 长度膨胀跨域传染 | 长度惩罚分域设定；推理力度拆独立专家 | DeepSeek-V4 三模式 |

### 5.4 评估侧

| 难点 | 解法 | 出处/实践者 |
|------|------|------------|
| 多维指标无法单一化 | 每域独立验证集 + 硬约束 early stopping（安全） | 工程惯例 |
| avg@n 横向误读 | 只看相对 step 1 的 Δ，不看绝对值（题库在动态变化） | MiMo-V2.6 仪表盘教训 |
| 训练健康度难判断 | 公开/监控：grad norm、entropy、KL、passrate 分布、成本/步 | MiMo-V2.6 仪表盘 |
| Reward hacking 发现晚 | 定期人工评估 + 多样性/格式惩罚项 | 工程惯例 |

## 6. 实践决策树与 Checklist

### 6.1 路线选择决策树

```
Q1: 各域奖励是否同构（都是可验证 0/1，且轨迹形态相近）？
    ├─ 是 → 可以 Mixed RL 直接混（如纯数学+纯代码）
    └─ 否 → Q2

Q2: 算力预算能否覆盖 "N 个专家 + 1 次蒸馏"？
    ├─ 能 → 专家分训 + MOPD/OPD（2026 头部厂商主流）
    └─ 不能 → Q3

Q3: 能否接受"分层叠加"（Reasoning→Agentic→General 逐阶段）？
    ├─ 能 → GLM-5 / Qwen3 式分阶段混合
    └─ 不能 → 单域 RL + 权重合并（Soup）凑合，
              接受能力互斥带来的损耗
```

### 6.2 Mixed RL 开工前 Checklist

- [ ] 所有奖励已 per-task 归一化到同一尺度？
- [ ] 有动态采样机制（剔太易/太难）而非静态配比？
- [ ] 每域独立验证集 + 每域指标实时监控？
- [ ] 训推一致性监控（train/infer KL）？
- [ ] MoE 负载均衡策略与 OOM 预案？
- [ ] 预算按"末步 token 量"而非"首步"估算？
- [ ] 安全域有硬约束（硬下限比例 + 硬阈值 early stop）而非软奖励？
- [ ] 长度惩罚分域设定，防跨域传染？
- [ ] 训崩可回滚到上一个好 checkpoint？

### 6.3 MOPD 开工前 Checklist

- [ ] 每个域的专家都已独立训到巅峰（学生上限 = 教师上限）？
- [ ] 学生模型容量足以装下所有教师能力（不足则扩 MoE）？
- [ ] KL 方向选反向（mode-seeking）？
- [ ] 全词表 logit 蒸馏的算力/显存预算充足？
- [ ] 蒸馏题库的领域分布 = 期望的能力配比？
- [ ] 教师权重 w_i 有消融实验支撑而非拍脑袋？
- [ ] On-policy 采样基础设施（异步 rollout）就位？
- [ ] 蒸馏后是否还需要一轮混合 RL 打磨（MiMo-V2.6 模式）？
